## วิธีจัดลำดับ
- จัดหมวดด้วย **MoSCoW** (Must / Should / Could / Won't this term)
- ภายในหมวดเดียวกัน เรียงตาม 4 ข้อ ตามลำดับความสำคัญ
  1. **Dependency** - งานที่งานอื่นต้องพึ่งต้องมาก่อน
  2. **Value** - ช่วยให้ปัญหาหลักหายไปมากแค่ไหน (นักศึกษาต้องเดินไปถามเจ้าหน้าที่ 5-10 นาที, เจ้าหน้าที่ตอบคำถามซ้ำ)
  3. **Risk** - งานที่มีความไม่แน่นอนสูงทำก่อน จะได้เจอปัญหาเร็ว
  4. **Effort** - ถ้าข้ออื่นใกล้กัน ให้งานที่เล็กกว่ามาก่อน
- Value / Risk / Effort ให้คะแนน 1-5 (5 = สูงสุด) ประเมินโดยทีม ณ วันที่อัปเดต

## บันทึกการเจรจา

### N-01 ฟังก์ชันจองอุปกรณ์ล่วงหน้า (Q-02) - 2569-10-02
**ผู้เข้าร่วม**: ตัวแทนนักศึกษา (ผู้ใช้), เจ้าหน้าที่ภาควิชา, อาจารย์หัวหน้าโครงการ (ผู้ตัดสิน), ทีมพัฒนา

**ประเด็น**: จะเอาฟังก์ชันจองล่วงหน้าเข้า scope เทอมนี้หรือไม่ และจัดอยู่หมวดไหน

| ฝ่าย | จุดยืน | สิ่งที่ต้องการจริง (interest) |
|---|---|---|
| ตัวแทนนักศึกษา | ต้องเป็น Must | ช่วงส่งโปรเจกต์อุปกรณ์มักไม่ว่าง อยากรู้ล่วงหน้าว่าจะได้ใช้เมื่อไร |
| เจ้าหน้าที่ภาควิชา | ไม่เอา | กลัวมีอุปกรณ์ที่จองแล้วไม่มีคนมารับ ต้องตามคนจองเพิ่ม และจะเสียงานมากขึ้น |
| ทีมพัฒนา | ไม่ทันเทอมนี้ | ต้องเพิ่มสถานะ "จองแล้ว" ซึ่งขัดกับ CON-DATA-01 (มีได้ 6 สถานะ) ทำให้ UC-02/07/08 ต้องเปลี่ยน และงาน Must ข้อ 1-7 ใช้เวลาหมดเทอมแล้ว |

**ทางเลือกที่คุยกัน**
1. Must เทอมนี้ - ตกไป เพราะต้องตัด UC-09 ออก ทำให้รอบยืม-คืนไม่ครบ
2. จองแบบง่าย (คิวรอ ไม่ล็อกอุปกรณ์) เป็น Could - ตกไป เพราะยังต้องเพิ่ม use case และแจ้งเตือนอยู่ดี งานไม่ได้เล็กลงจริง
3. **Won't เทอมนี้ แต่ให้ UC-01 แสดงกำหนดคืนโดยประมาณ (FR-EQS-04)** เพื่อให้นักศึกษาวางแผนได้ - **ตกลงใช้ข้อนี้**

**ข้อตกลง**
- Q-02 อยู่ในหมวด Won't (เทอมนี้) และเก็บไว้เป็นงานแรกที่จะพิจารณาในเทอมถัดไป
- FR-EQS-04 (แสดงกำหนดคืนให้นักศึกษาเห็น) เป็นสิ่งที่แลกมาแทนการจอง ถ้าจะเปลี่ยนต้องผ่าน change request
  (ดู [CR-001](changes/CR-001.md))
