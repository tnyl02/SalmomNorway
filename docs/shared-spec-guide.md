# คู่มือ specs/000-shared: ของที่หลายฟีเจอร์ใช้ร่วมกัน อยู่ที่ไหน

พอมีฟีเจอร์ที่ 2 จะเจอคำถามว่า Constraint, ข้อมูล และคำศัพท์ที่ทุกฟีเจอร์ใช้ ควร copy ไปทุก spec ไหม
คำตอบคือ **ไม่ copy** เขียนที่เดียวใน `specs/000-shared/` แล้วให้ spec ของฟีเจอร์อ้าง ID

## 1. ของ 4 อย่าง อยู่ 4 ที่

| อะไร | ตัวอย่าง | อยู่ที่ไหน | ใครเปลี่ยนได้ |
|---|---|---|---|
| กติกาการทำงานของ AI | ห้ามเดา ห้ามเพิ่มฟีเจอร์ ต้องอ้าง ID | `AGENTS.md` | ทีม (ไม่ใช่ requirement) |
| Constraint ที่ใช้ทุกฟีเจอร์ | ฐานข้อมูล PostgreSQL, PDPA, ยืนยันตัวตนก่อน, อ้างด้วย HN | `specs/000-shared/constraints.md` | ผู้ใช้หรือฝ่าย IT ผ่าน CR |
| Constraint เฉพาะฟีเจอร์ | ฟีเจอร์ชำระเงินต้องต่อ payment gateway ของโรงพยาบาล | หมวด Constraints ใน `specs/NNN-*/spec.md` | ผู้ใช้ผ่าน CR |
| ค่าที่ตั้งได้ (ตัวเลขและกฎ) | 30 วัน, 3 ตัวเลือก, ส่งซ้ำ 3 ครั้งห่าง 5 นาที | อยู่ใน FR ที่เป็นเจ้าของตัวเลข ส่วนในโค้ดอยู่ที่ `backend/app/config.py` ที่เดียว | ผู้ใช้ผ่าน CR แล้วแก้ config.py |

ข้อมูลร่วม (Patient, Slot, Booking) อยู่ที่ `specs/000-shared/data-model.md` และคำศัพท์อยู่ที่ `glossary.md`

## 2. หน้าตาของหมวด Constraints ใน spec ฟีเจอร์

```
## Constraints
ใช้ร่วม (ข้อความเต็มอยู่ที่ specs/000-shared/constraints.md ห้าม copy มาไว้ที่นี่):
- CON-TECH-01 ฐานข้อมูล PostgreSQL
- DOM-PDPA-01 audit log ทุกครั้งที่เข้าถึงข้อมูลสุขภาพ
- IF-IDP-01 ต้องยืนยันตัวตนก่อน
เฉพาะฟีเจอร์นี้:
- IF-PAY-01 ชำระเงินผ่าน payment gateway ของโรงพยาบาลเท่านั้น ไม่เก็บเลขบัตรเครดิต
```

- บรรทัด "ใช้ร่วม" เขียนแค่ ID กับคำสั้น ๆ ให้คนอ่านรู้ว่าคืออะไร ข้อความเต็มมีที่เดียว
- Constraint ที่อ้างว่าใช้ร่วม นับเป็น Constraint ของฟีเจอร์นี้ทุกข้อ: plan ข้อ 5, tasks และ rtm.md ต้องมีครบ (คำสั่งทุกตัวรู้กติกานี้แล้ว)
- ถ้าเขียน Constraint ซ้ำทั้ง 2 ที่ /clarify จะทักว่าต้องมีที่เดียว

## 3. ทำไมต้องที่เดียว

- แก้ครั้งเดียวถึงทุกฟีเจอร์ เช่น ฝ่าย IT เปลี่ยนฐานข้อมูล แก้ CON-TECH-01 ที่เดียว แล้วดูตาราง "ใครอ้างใช้บ้าง" ว่ากระทบฟีเจอร์ไหน
- ไม่เกิดเวอร์ชันที่ต่างกันเงียบ ๆ (ฟีเจอร์ A บอกเก็บ log 1 ปี ฟีเจอร์ B บอก 2 ปี)
- /verify ของทุกฟีเจอร์ตรวจ Constraint ชุดเดียวกัน

## 4. แก้ Constraint ร่วม = CR ที่กระทบหลายฟีเจอร์

1. เขียน CR ใน `specs/changes/` ระบุว่าแก้ ID ไหนใน constraints.md
2. Impact Analysis: เปิดตาราง "ใครอ้างใช้บ้าง" ท้าย constraints.md แล้วเปิด rtm.md ของแต่ละฟีเจอร์ที่อ้าง ดูว่าโค้ดและ test ไหนกระทบ
3. ผู้ใช้ยืนยันแล้ว จึงแก้ constraints.md ขึ้นเวอร์ชัน และเพิ่ม CHANGELOG 1 รายการ
4. รัน /verify ทุกฟีเจอร์ที่อ้าง ID นั้น

## 5. ทีมที่มี 1 ฟีเจอร์อยู่แล้ว ย้ายอย่างไร

ทำตอนเปิดฟีเจอร์ที่ 2 ไม่ต้องทำก่อนหน้านั้น

1. สร้าง `specs/000-shared/constraints.md` ตามแบบใน template แล้วย้าย Constraint ที่ฟีเจอร์ที่ 2 ต้องใช้ด้วย ไปไว้ที่นั่น **ใช้ ID และข้อความเดิม**
2. ใน spec ฟีเจอร์ที่ 1 เปลี่ยนข้อที่ย้ายไปเป็นบรรทัด "ใช้ร่วม" ขึ้นเวอร์ชัน และเพิ่ม CHANGELOG (ไม่ต้องทำ CR เพราะข้อความและ ID ไม่เปลี่ยน)
3. รัน `/clarify` กับ spec ฟีเจอร์ที่ 1 หนึ่งรอบ ให้ AI เช็กว่าไม่มี ID หายหรือซ้ำ
4. plan.md, tasks.md, โค้ด และ test ของฟีเจอร์ที่ 1 **ไม่ต้องแก้** เพราะ ID เดิม
5. ฟีเจอร์ที่ 2 เขียนบรรทัด "ใช้ร่วม" ตั้งแต่ spec v1

## 6. ค่าที่ตั้งได้ ทำไมต้องอยู่ใน config.py

ตัวเลขอย่าง "30 วัน" เป็น requirement (อยู่ใน FR-BKG-01) แต่พอเป็นโค้ด ถ้าฝังไว้ 4 ที่ วันที่ผู้ใช้เปลี่ยนเป็น 45 วัน จะแก้ไม่ครบ
plan.md ข้อ 5 จึงมีตาราง "ค่าที่ตั้งได้" บอกว่าตัวเลขไหนมาจาก ID ไหน และชื่อตัวแปรอะไรใน `backend/app/config.py`

```python
# backend/app/config.py
DAYS_AHEAD = 30          # FR-BKG-01 แสดงช่วงว่างภายใน 30 วันข้างหน้า
ALT_SLOT_COUNT = 3       # FR-BKG-03 เสนอช่วงใกล้เคียง 3 ตัวเลือก
NOTIFY_RETRY_MAX = 3     # ASM-03 ส่งซ้ำสูงสุด 3 ครั้ง
NOTIFY_RETRY_MINUTES = 5 # ASM-03 ห่างกัน 5 นาที
```

/verify คำถามข้อ 2 จะหาตัวเลขที่ฝังในโค้ดแทนที่จะอยู่ใน config.py ให้ และ /implement จะเพิ่มตัวแปรใน config.py ให้เองเมื่อ task ต้องใช้
