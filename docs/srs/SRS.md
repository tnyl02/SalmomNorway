## 1. Introduction

### 1.1 วัตถุประสงค์ของเอกสาร
รวบรวมความต้องการทั้งหมดของระบบยืมอุปกรณ์ภาควิชาคอมพิวเตอร์ไว้เป็นแหล่งความจริงเดียว สำหรับทีมพัฒนา ผู้ทดสอบ และ AI coding agent
spec.md ของแต่ละฟีเจอร์ใน `specs/` คัดมาจากเอกสารนี้เฉพาะข้อที่ทดสอบได้

### 1.2 ขอบเขตของระบบ
- ปัญหา (Journey Map): นักศึกษาตรวจสอบสถานะอุปกรณ์เองไม่ได้ ต้องสอบถามเจ้าหน้าที่ใช้เวลา 5-10 นาที
  ข้อมูลการยืมเขียนด้วยมือ ตรวจสอบย้อนหลังยาก และเอกสารขออนุมัติค้างคืนต้องเดินหาลายเซ็น
- เป้าหมาย: นักศึกษาตรวจสอบสถานะและส่งคำขอยืมได้ด้วยตนเอง เจ้าหน้าที่บันทึกรอบยืม-คืนในระบบเดียว
- ในขอบเขต: use case UC-01 ถึง UC-15 ตาม Use Case Diagram (หัวข้อ 3.1)
- นอกขอบเขตเทอมนี้: จองอุปกรณ์ล่วงหน้า (BL-11, Won't ตามข้อตกลง N-01 ใน `specs/backlog.md`)

### 1.3 คำนิยามและคำย่อ
ดู `specs/000-shared/glossary.md` (ใช้คำเดียวกันทั้งเอกสาร)
คำย่อ: RQ = ข้อในตาราง Requirement บน Miro, FR = Functional Requirement, NFR = Non-Functional Requirement,
AC = Acceptance Criteria, UC = Use Case, US = User Story, BL = Backlog item, CR = Change Request, RTM = Requirements Traceability Matrix

## 2. Overall Description

### 2.1 ภาพรวมระบบและความสัมพันธ์กับระบบอื่น (System Context)
| ฝ่าย / ระบบ | แลกเปลี่ยนอะไรกับระบบเรา | ทิศทาง | ที่มาใน Miro |
|---|---|---|---|
| นักศึกษา | ค้นหาอุปกรณ์ ส่ง/ยกเลิกคำขอยืม ยืนยันรับ แจ้งคืน ดูสถานะคำขอ | เข้า-ออก | Use Case Diagram, System Context |
| เจ้าหน้าที่ (นักเทคโนโลยีสารสนเทศ / นักคอมพิวเตอร์) | อนุมัติคำขอปกติ ส่งมอบ รับคืน ตรวจสภาพ จัดการอุปกรณ์ บันทึกผลอนุมัติค้างคืน | เข้า-ออก | Use Case Diagram, System Context |
| อาจารย์หัวหน้าโครงการ | เซ็นอนุมัติเอกสารค้างคืน**นอกระบบ** เจ้าหน้าที่นำผลเข้าระบบ (RQ-15) | ไม่ได้ใช้ระบบโดยตรง | Architecture, System Context |
| ระบบยืนยันตัวตนของมหาวิทยาลัย | ผลยืนยันตัวตน บทบาท และภาควิชา ผ่าน Auth API (RQ-23, IF-IDP-01) | เข้า | Use Case Diagram, Architecture |
| ระบบแจ้งเตือน Email | ข้อความแจ้งผลอนุมัติ และเตือนก่อนถึงกำหนดคืน (RQ-12, RQ-21, IF-NOT-01) | ออก | Use Case Diagram, Architecture |

### 2.2 กลุ่มผู้ใช้และคุณลักษณะ (จาก Stakeholder Register และ Onion Diagram)
| กลุ่ม | ใช้ระบบทำอะไร | Power / Interest | สิ่งที่ห้ามเห็น |
|---|---|---|---|
| นักศึกษา | ผู้ใช้หลัก ยืม-คืนสะดวก เช็กสถานะได้ทันที | ต่ำ / สูง | ชื่อผู้ยืมรายอื่น (DOM-PRIV-01), อุปกรณ์ภาควิชาอื่น (DOM-ACCESS-01) |
| นักคอมพิวเตอร์ | ดูแลอุปกรณ์ ติดตามสถานะ ลดงานเอกสาร | สูง / สูง | - |
| นักเทคโนโลยีสารสนเทศ | ดูแลระบบ ความปลอดภัย บัญชีผู้ใช้ | สูง / สูง | - |
| อาจารย์หัวหน้าโครงการ | ไม่ใช้ระบบโดยตรง อนุมัติค้างคืนนอกระบบ ต้องการรายงานสรุป | สูง / ต่ำ | - |

### 2.3 สภาพแวดล้อมการทำงาน (Infrastructure)
- ผู้ใช้เข้าผ่านเว็บ responsive ทั้งคอมพิวเตอร์และมือถือ (เว็บนักศึกษา และแดชบอร์ดเจ้าหน้าที่)
- ระบบทำงานใน Docker บน on-campus server หรือ cloud VM ผ่าน HTTPS มี backup รายวัน (CON-TECH-02)
- ฐานข้อมูล PostgreSQL (CON-TECH-01), ที่เก็บไฟล์สำหรับรูปสภาพอุปกรณ์และเอกสารแนบ (RQ-04, RQ-16), audit log

### 2.4 ข้อจำกัด
ข้อความเต็มที่ `specs/000-shared/constraints.md`: CON-TECH-01, CON-TECH-02, CON-DATA-01 (สถานะ 3 ค่า), CON-DATA-03, DOM-LOAN-01

### 2.5 ข้อสมมติและสิ่งที่ต้องพึ่งพา
- ASM-01 ข้อมูลอุปกรณ์ตั้งต้นถูกนำเข้าระบบโดยเจ้าหน้าที่ก่อนเปิดใช้งานจริง
- ASM-02 ระบบยืนยันตัวตนใช้บัญชีของมหาวิทยาลัยที่มีอยู่แล้ว ผ่าน Auth API
- ASM-03 ประเภทอุปกรณ์ (category) อ่านจากข้อมูลที่เจ้าหน้าที่กำหนดไว้แล้วใน UC-10
- พึ่งพา: ระบบยืนยันตัวตนต้องส่งภาควิชาของผู้ใช้กลับมา ถ้าไม่ส่ง ทำ DOM-ACCESS-01 ไม่ได้ (Q-SH-03)
