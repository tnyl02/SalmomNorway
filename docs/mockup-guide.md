# คู่มือ mockup: เอาหน้าจอที่คุยกับผู้ใช้ มาใช้เป็นแบบตอนเขียนโค้ด

mockup คือหน้าจอตัวอย่างที่ใช้คุยกับผู้ใช้หรือ PO จนตกลงกันแล้ว
mockup จึงเป็น **ส่วนหนึ่งของ requirement** ต้องเก็บไว้คู่กับ spec ไม่ใช่เก็บไว้กับโค้ด

## 1. วางไว้ที่ไหน

```
specs/
  CHANGELOG.md
  000-shared/
    mockups/                       # ส่วนที่ทุกหน้าใช้ร่วมกัน เช่น header เมนู สี (ถ้ามี)
  001-booking/
    spec.md                        # มีหมวด "หน้าจอ (UI)" ชี้ไปที่ไฟล์ใน mockups/
    plan.md
    tasks.md
    mockups/
      UI-BKG-01-select-slot.html   # ให้ AI อ่าน
      UI-BKG-01-select-slot.png    # ให้คนดู และให้ PO ยืนยัน
frontend/src/                      # โค้ดจริงเท่านั้น ห้ามวาง mockup ที่นี่
```

- ห้ามวางใน `frontend/src/` เพราะ AI อาจคิดว่าเป็นโค้ดจริง แล้วยกไปใช้ทั้งไฟล์
- ห้ามวางใน `frontend/public/` เพราะไฟล์ในนั้นจะถูกเปิดขึ้นเว็บไปด้วย

## 2. ตั้งชื่อไฟล์

`UI-<ตัวย่อฟีเจอร์>-<เลข>-<ชื่ออังกฤษสั้น ๆ>.html` และภาพ .png ชื่อเดียวกัน
เลข UI ใช้ใน spec plan tasks และ rtm เหมือน ID อื่น ๆ

## 3. เริ่มจากอะไร: 3 กรณี

| ทีมมีอะไรอยู่ | ทำอย่างไร |
|---|---|
| ยังไม่มี mockup เลย | คัดลอก `docs/mockup-template.html` ไปที่ `specs/00N-<feature>/mockups/UI-xxx-NN-<ชื่อ>.html` แล้วแก้ข้อความและช่องให้ตรงที่คุยกับผู้ใช้ เปิดในเบราว์เซอร์ จับภาพเป็น .png ให้ PO ยืนยัน |
| มีภาพจาก UX/UI แล้ว (PNG, ภาพจาก Figma) | วางภาพไว้ใน `mockups/` ก่อน แล้วให้ AI แปลงภาพเป็น HTML ด้วยข้อความสั่งด้านล่าง จากนั้นคนเปิดเทียบกับภาพว่าข้อความและช่องครบ แล้วให้ PO ยืนยันอีกครั้ง |
| มีไฟล์ HTML หรือ prototype อยู่แล้ว | ถ้าไฟล์เดียวจบและไม่มี JavaScript วางได้เลย ถ้ามีหลายไฟล์หรือมี JavaScript ให้ AI ย่อเป็นไฟล์เดียวตามแบบ `docs/mockup-template.html` |

ข้อความสั่ง AI แปลงภาพเป็น HTML (แนบภาพในแชตด้วย เพราะบางเครื่องมืออ่านไฟล์ภาพใน repo เองไม่ได้)

```
แปลงภาพหน้าจอนี้เป็น static HTML ไฟล์เดียว ตามโครงใน docs/mockup-template.html
ใช้ข้อความภาษาไทยตามภาพทุกตัวอักษร ใช้ข้อมูลตัวอย่าง ไม่ใส่ JavaScript
ใส่ data-req ที่ปุ่มและช่องตาม FR ใน specs/00N-<feature>/spec.md ถ้าส่วนไหนหา FR รองรับไม่เจอ ให้เขียนรายการบอก ห้ามเดา
บันทึกเป็น specs/00N-<feature>/mockups/UI-xxx-NN-<ชื่อ>.html แล้วจดใน prompt-log
```

## 4. กติกาของไฟล์ HTML

- ไฟล์เดียวจบ ใส่ CSS ไว้ในไฟล์ ไม่มี JavaScript ไม่มี logic
- ใช้ข้อความภาษาไทยจริงตามที่จะขึ้นบนจอ ส่วนข้อมูล (ชื่อ วันที่ ตัวเลข) เป็นข้อมูลตัวอย่าง
- ถ้าหน้าเดียวมีหลายสถานะ (ปกติ เต็ม ผิดพลาด) วางทุกสถานะไว้ในไฟล์เดียว แยกกล่องและเขียนชื่อสถานะกำกับ
- ใส่ `data-req="FR-xxx-NN"` ที่ปุ่ม ช่อง หรือกล่องข้อความ เพื่อบอกว่าส่วนนั้นรองรับ requirement ข้อไหน
- ปุ่มนำทางระหว่างขั้น (ถัดไป กลับ) ไม่ต้องมี FR รองรับ แต่ปุ่มที่ทำงานกับข้อมูล (จอง ยกเลิก แก้ไข) ต้องมี FR เสมอ
- เรื่องที่ยังเป็น Q-xx **ห้ามเดาใน mockup** ให้ใช้กล่องที่เขียนว่า "รอ Q-xx" แทน
- ภาพ .png ได้จากการเปิดไฟล์ HTML ในเบราว์เซอร์แล้วจับภาพหน้าจอ

## 5. เขียนหมวด "หน้าจอ (UI)" ใน spec.md

วางไว้ก่อนหมวด Assumptions & Open Questions แต่ละหน้าบอก 3 อย่าง: รองรับ FR ข้อไหน อะไรต้องตรง อะไรยืดหยุ่นได้

```
## หน้าจอ (UI)
- UI-BKG-02 ยืนยันการจอง: mockups/UI-BKG-02-confirm.html (3 สถานะ)
  รองรับ: FR-BKG-02, FR-BKG-03, FR-BKG-04
  ต้องตรง: ปุ่ม "ยืนยันการจอง" ข้อความ "ช่วงเวลาเต็ม" และแสดง 3 ตัวเลือกพร้อมวันและเวลา
  ยืดหยุ่นได้: ข้อความอธิบายอื่น ๆ สี ระยะห่าง
```

ถ้าไม่บอกว่าอะไรต้องตรง AI จะเดาเอง บางครั้งลอกทุกพิกเซล บางครั้งไม่สนใจ mockup เลย

## 6. ถ้า mockup กับ spec ขัดกัน

**ถือ spec เป็นหลักเสมอ** เช่น mockup มีปุ่ม "ยกเลิกการจอง" แต่ spec บอกว่าการยกเลิกอยู่ใน Out of scope
ปุ่มนั้นคือของแถมที่แอบเข้ามาทาง mockup ให้เอาออกจาก mockup หรือเขียนเป็น Q-xx หรือ CR ถ้าผู้ใช้ต้องการจริง

## 7. เพิ่ม mockup ทีหลัง ต้องรันอะไรใหม่บ้าง

ไม่ต้องรันใหม่ทั้งหมด ทำเฉพาะส่วนที่เกี่ยวกับหน้าจอ

| งานที่มีอยู่แล้ว | ต้องทำอะไร |
|---|---|
| spec.md | เพิ่มหมวด "หน้าจอ (UI)" ขึ้นเวอร์ชันใหม่ และเพิ่ม 1 รายการใน `specs/CHANGELOG.md` ถ้าไม่เปลี่ยน FR และ AC ไม่ต้องทำ CR |
| ตรวจว่าขัดกันไหม | รัน `/clarify` 1 รอบ AI จะเทียบ mockup กับ spec ให้ (ขั้นที่ 1 อ่านอย่างเดียว ไม่แก้ไฟล์) |
| plan.md | **ไม่ต้องรัน /plan ใหม่** เพราะจะเขียนทับทั้งไฟล์ ให้แก้เฉพาะหัวข้อ 4 (ใช้ข้อความสั่งด้านล่าง) |
| tasks.md | **ไม่ต้องรัน /tasks ใหม่** เพิ่มช่อง "แบบหน้าจอ" ให้ task หน้าจอ (ใช้ข้อความสั่งด้านล่าง) |
| task หน้าจอที่ยังไม่ทำ | `/implement` ตามปกติ AI จะเปิด mockup จากช่อง "แบบหน้าจอ" เอง |
| task หน้าจอที่ทำเสร็จแล้ว | ไม่ต้องทำใหม่ รัน `/verify` แล้วดูข้อค้นพบชนิด "ไม่ตรง mockup" แก้ทีละข้อ |
| task หลังบ้าน | ไม่ต้องแก้อะไร |

ข้อความสั่งในแชตสำหรับแก้ plan.md

```
แก้เฉพาะหัวข้อ 4 ใน specs/001-booking/plan.md เพิ่ม UI ID และไฟล์ mockup ให้หน้าจอแต่ละหน้า ตามหมวด "หน้าจอ (UI)" ใน spec.md ห้ามแก้หัวข้ออื่น แล้วจดใน prompt-log
```

ข้อความสั่งในแชตสำหรับแก้ tasks.md

```
เพิ่มช่อง "แบบหน้าจอ" ใต้ช่อง "ไฟล์ที่แตะ" ให้ทุก task ใน specs/001-booking/tasks.md task หน้าจอใส่ UI ID และไฟล์ mockup ตามหัวข้อ 4 ใน plan.md task อื่นใส่ "ไม่มี" ห้ามแก้ช่องอื่น ห้ามเปลี่ยนสถานะ แล้วจดใน prompt-log
```

แล้ว commit ทั้งหมดในครั้งเดียว

```
git add -A && git commit -m "spec v3: add UI mockups" && git push
```

## 8. คำสั่งไหนอ่าน mockup บ้าง

| คำสั่ง | ทำอะไรกับ mockup |
|---|---|
| /clarify | หาสิ่งที่ mockup กับ spec ขัดกัน แล้วเสนอเป็นคำถาม |
| /plan | ใส่ UI ID และไฟล์ mockup ให้หน้าจอแต่ละหน้าในหัวข้อ 4 |
| /tasks | ใส่ช่อง "แบบหน้าจอ" ให้ task หน้าจอ |
| /implement และ /implement-all | เปิด mockup ก่อนเขียนหน้าจอ ทำส่วนที่ "ต้องตรง" ให้ตรง |
| /testcases | ใช้ข้อความบนจอจาก mockup ได้ ถ้าหมวด UI บอกว่า "ต้องตรง" |
| /verify | คำถามข้อ 6 เทียบหน้าจอจริงกับ mockup |
