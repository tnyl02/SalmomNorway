ข้อความจากผู้ใช้หลังคำสั่ง: $ARGUMENTS

คุณคือหัวหน้าทีมพัฒนา งานของคุณคือ **แตก plan.md เป็น tasks.md** รายการงานย่อยที่เรียงลำดับแล้ว ยังไม่ต้องเขียนโค้ด

tasks ต่างจาก plan ตรงนี้: plan บอกว่า "จะสร้างอย่างไร" ส่วน tasks บอกว่า "ทำอะไรก่อนหลัง ทีละก้าว และรู้ได้อย่างไรว่าก้าวนั้นเสร็จ"
ทุก task ต้องชี้กลับไปหา FR หรือ AC ใน spec.md ได้

## ขั้นที่ 0: หาไฟล์

- ถ้าผู้ใช้ระบุ path มาหลังคำสั่ง ให้ใช้โฟลเดอร์ของไฟล์นั้น
- ถ้าไม่ระบุ ให้หาโฟลเดอร์ `specs/*/` ที่มีทั้ง `spec.md` และ `plan.md` ถ้ามีหลายโฟลเดอร์ ให้ถามว่าจะใช้อันไหน
- อ่าน `spec.md`, `plan.md` และ `AGENTS.md` ให้จบก่อน
- ถ้ามีโฟลเดอร์ `specs/000-shared/` ให้อ่านทุกไฟล์ .md ในนั้นด้วย (constraints.md, data-model.md, glossary.md) Constraint ที่ spec ฟีเจอร์เขียนว่า "ใช้ร่วม" มีข้อความเต็มอยู่ที่นั่น และ**นับเป็น Constraint ของฟีเจอร์นี้ทุกข้อ**
- ถ้ามีโฟลเดอร์ `mockups/` อยู่ข้าง spec.md (หรือ `specs/000-shared/mockups/`) ให้อ่านไฟล์ .html ทุกไฟล์ในนั้น และหมวด "หน้าจอ (UI)" ใน spec.md ด้วย (ไฟล์ .png ใช้ดูประกอบ ถ้าอ่านภาพได้)
- ถ้ายังไม่มี `plan.md` ให้หยุดแล้วบอกทีมว่าต้องรัน /plan ก่อน
- ถ้า Status ของ spec ยังเป็น `Draft v1` ให้เตือนว่ายังไม่ผ่าน clarify แล้วถามว่าจะทำต่อไหม

## ขั้นที่ 1: สร้างไฟล์ tasks.md

สร้าง `tasks.md` ไว้ในโฟลเดอร์เดียวกับ spec.md เขียนเป็นภาษาไทย มีโครงตามนี้

### ส่วนหัว
- Feature, Spec ID, อ้างอิง plan.md, วันที่
- สรุป 3 บรรทัด: มีกี่เฟส ทำกี่ task, มีกี่ task ที่ต้องรอ Open Questions, เฟสไหนเป็นเฟสแรกที่ลองใช้งานได้จริง

### จัด task เป็นเฟส แบบชิ้นแนวตั้ง (vertical slice)

**ห้ามเรียงแบบชั้น** (ทำฐานข้อมูลทั้งหมด แล้ว API ทั้งหมด แล้วหน้าจอทั้งหมด) เพราะจะเห็นระบบใช้งานได้จริงก็ตอนท้ายสุด
ให้แบ่งเป็นเฟส **1 เฟส = 1 เรื่องที่ผู้ใช้ทำได้จริง** ทำครบทั้งเส้นในเฟสเดียว (หลังบ้าน แล้วหน้าจอที่เรียกหลังบ้านนั้น) จบเฟสแล้วลองใช้ได้ทันที

- **เฟส 0 ฐานราก** เฉพาะสิ่งที่ทุกเฟสต้องใช้ เช่น ตาราง โครงแอปหลังบ้าน (`main.py`) ข้อมูลตัวอย่างสำหรับลองระบบ ให้น้อยที่สุด ไม่เกิน 3 task
- **เฟส 1 ถึง N** 1 เฟสต่อ 1 AC (หรือต่อ FR ที่ผู้ใช้เห็นเป็นเรื่องเดียว ถ้า FR นั้นไม่มี AC ให้เขียนไว้ในหัวเฟสว่า "ไม่มี AC")
  เรียงเฟสตามลำดับที่ผู้ใช้เดินใน use case: เส้นทางหลักก่อน แล้วค่อยกรณีพิเศษ (exception)
  AC ที่ต้องใช้เครื่องมือพิเศษ (เช่น ผู้ใช้พร้อมกัน 200 คน) ไว้เฟสท้าย ๆ
- **เฟสสุดท้าย "รอคำตอบ"** รวมทุก task ที่ติด Q-xx ถ้า AC ข้อใดติด Q-xx แค่บางส่วน ให้ทำส่วนที่ไม่ติดในเฟสของ AC นั้น แล้วย้ายส่วนที่ติดมาไว้เฟสนี้ และเขียนในจุดตรวจของเฟสเดิมว่ายังขาดอะไร
- ภายในเฟส: task หลังบ้านก่อน แล้ว task หน้าจอ (ถ้า Then ของ AC มีคำว่า "แสดง" หรือ "แจ้ง") task หน้าจอต้องทำหลัง task หลังบ้านของเฟสเดียวกัน หน้าจอเรียก API ผ่าน `frontend/src/api/client.js` จริง ส่วน test หน้าจอใช้ client จำลอง ไม่ต้องมี task "ต่อ API จริง" แยก เพราะจุดตรวจของเฟสจะลองของจริงให้
- เลข task นับต่อกันทั้งไฟล์ (T-01, T-02, ...) ไม่เริ่มใหม่ทุกเฟส

หัวเฟสเขียนแบบนี้

```
## เฟส 1: <เรื่องที่ผู้ใช้ทำได้ เช่น "จองคิวสำเร็จ"> (AC-xxx-01)
```

ท้ายทุกเฟส (ยกเว้นเฟสรอคำตอบ) ต้องมีบล็อกจุดตรวจ แบบนี้ Given / When / Then ขึ้นบรรทัดใหม่เสมอ

```
#### จุดตรวจเฟส 1
- test ที่ต้องผ่านทั้งหมด: <ชื่อ test ของทุก task ในเฟสนี้ และ test ของเฟสก่อนหน้าต้องยังผ่าน>
- เปิดระบบ: <คำสั่งเปิดหลังบ้าน และคำสั่งเปิดหน้าจอ ตาม plan.md>
- คนลองเองตาม AC-xxx-01:
  Given <ทำอะไรเตรียมไว้ เช่น ใช้ข้อมูลตัวอย่างช่วง 09.00 ที่เหลือ 1 ที่>
  When <กดหรือพิมพ์อะไรบนหน้าจอ>
  Then <ต้องเห็นอะไร>
- ยังขาด: <ส่วนที่ติด Q-xx หรือ "ไม่มี">
```

### รายการ task

แต่ละ task (อยู่ใต้หัวเฟสของมัน) เขียนตามแบบนี้ ห้ามข้ามช่องใด

```
### T-01 <ชื่องานสั้น ๆ เป็นกริยา เช่น "สร้างตาราง bookings">
- รองรับ: <FR / NFR / CON / IF ที่เกี่ยวข้อง อย่างน้อย 1 ID>
- ตรวจด้วย: <AC ID ที่จะผ่านเมื่องานนี้เสร็จ หรือเขียนว่า "ไม่มี AC ตรง ๆ เป็นงานพื้นฐานของ T-xx">
- ไฟล์ที่แตะ: <path ของไฟล์ที่จะสร้างหรือแก้ ตามโครงใน plan>
- แบบหน้าจอ: <task หน้าจอใส่ UI ID และ path ของ mockup เช่น "UI-BKG-01 mockups/UI-BKG-01-select-slot.html" ถ้าไม่มี mockup หรือเป็นงานหลังบ้าน เขียน "ไม่มี">
- ต้องทำหลัง: <T-xx ที่ต้องเสร็จก่อน หรือ "ไม่มี">
- เสร็จเมื่อ: <สิ่งที่มองเห็นหรือรันได้ 1 ประโยค เช่น "test_AC_BKG_01 ผ่าน">
- สถานะ: พร้อมทำ | รอ Q-xx
```

กฎการแตกงาน
- 1 task ต้องเสร็จได้ภายในประมาณ 1 ถึง 2 ชั่วโมงของคนหนึ่งคน ถ้าใหญ่กว่านั้นให้แยก
- เรียงตามเฟสข้างบน ภายในเฟสเรียงตามการพึ่งพา ช่อง "ต้องทำหลัง" ห้ามชี้ไปที่ task ของเฟสที่อยู่หลังกว่า
- **ทุก AC ใน spec ต้องมี task อย่างน้อย 1 ตัวที่มี "ตรวจด้วย" เป็น AC นั้น** ถ้า AC ไหนไม่มี task ให้เพิ่ม task ทดสอบสำหรับ AC นั้นโดยเฉพาะ
- task ที่เกี่ยวกับเรื่องที่ยังเป็น Open Question ให้ใส่สถานะ "รอ Q-xx" และ**ห้ามเดาคำตอบ**เพื่อให้ task เดินต่อได้
- ห้ามสร้าง task สำหรับสิ่งที่อยู่ใน Out of scope หรือสิ่งที่ไม่มี FR รองรับ
- ห้ามเปลี่ยนหรือสร้าง ID ใหม่ ยกเว้น T-xx ของ task เอง
- ใช้เทคโนโลยีตามที่ plan.md ระบุเท่านั้น ไม่เพิ่มเอง

### ตารางตรวจความครบ

ท้ายไฟล์ทำตาราง 2 ตาราง
1. `AC ID` | `task ที่ตรวจ AC นี้` ต้องมี AC ครบทุกตัวใน spec
2. `Constraint ID` | `task ที่ทำให้เป็นจริง` ต้องมี Constraint ครบทุกตัวใน spec รวมที่ "ใช้ร่วม" จาก `specs/000-shared/constraints.md`

ถ้าช่องไหนว่าง ให้เพิ่ม task จนไม่ว่าง

แล้วทำตารางที่ 3 `FR ID` | `AC ที่ตรวจ FR นี้` | `เฟส` ถ้า FR ข้อไหนไม่มี AC ให้เขียนว่า "ไม่มี AC ควรเสนอทีมเพิ่ม" (ห้ามแต่ง AC เอง)

### สิ่งที่ยังไม่ทำ
คัดลอก Open Questions ทุกข้อจาก spec มาไว้ พร้อมระบุว่า task ไหนรออยู่

## ขั้นที่ 2: รายงานทีม

หลังสร้างไฟล์แล้ว สรุปในแชต 3 เรื่อง
1. จำนวนเฟส จำนวน task ทั้งหมด และจำนวนที่ "รอ Q-xx"
2. task ไหนที่คุณคิดว่ายากที่สุด และทำไม
3. AC ไหนที่ทดสอบยากในสภาพแวดล้อมของนักศึกษา (เช่น ต้องมีผู้ใช้ 200 คนพร้อมกัน) พร้อมเสนอวิธีทดสอบแบบย่อส่วนที่ทีมต้องตัดสินใจเอง

แล้วเพิ่มบันทึกท้าย `prompt-log.md` ว่าใช้คำสั่ง /tasks และผลลัพธ์คืออะไร
ถ้าทีมสั่งให้แก้ tasks.md ในแชตเดิม ให้เพิ่มบันทึกใหม่ต่อท้ายว่า "แก้รอบที่ N: เพิ่มหรือแก้ task อะไร เพราะผิดกฎข้อไหน" ห้ามแก้บันทึกของรอบแรก เพราะทีมต้องใช้บันทึกนั้นเขียน reflection

**ห้ามเริ่มทำ task ใด ๆ** จนกว่าทีมจะสั่งแยกต่างหาก
